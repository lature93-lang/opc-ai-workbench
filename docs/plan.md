# OPC 个人 AI 工作台 方案定稿

方案已经 17 在第二确认点通过。定稿已包含以下更正：滴答清单和微信桥都已接通，DeepSeek Harness 已弃用，skill 只写中文。

## 一、功能清单
1. 入口：17 只跟总助对接，可以通过微信（ClawBot 桥，已接通）或 Grok Bot 主窗口。
2. 日程与决策：用 Notion 数据库「项目事项」存档，设看板、日历、待我决定三个视图；用滴答清单的「17项目日程」清单做提醒（官方 Open API，OAuth 授权，已接通）。
3. 需求到上线：顺序是客户经理、产品经理、开发者、质检员，每步做完都交回总助。全程有四个点要 17 确认：需求定义、方案设计、MVP 演示、最终验收。
4. 工具分工：云端开发 agent 管 GitHub（开分支、提 PR）；17 电脑上的 Codex 管本地项目，要求电脑在线，每条命令都要 17 批准。DeepSeek Harness 已弃用，不再作为中间层。
5. 规则：密钥只通过加密输入框提供；对外发消息必须经 17 同意；交付按高标准验收。

## 三、任务拆分

### T1 建仓库和基础结构（P0）
- 目标：在 lature93-lang 下建私有仓库 opc-ai-workbench，按上面的目录建好文件，并写好 .gitignore 和 README。
- 验收标准：仓库是私有的；目录和上面一致；.gitignore 覆盖 .env、*.key 和文件名含 token 的文件；仓库里没有任何密钥。

### T2 写 SKILL.md（P0）
- 目标：按下面的 10 章大纲写完，全部用中文，写成 Grok Bot 能直接当 skill 执行的样子。
- 章节：1. 用途和触发条件；2. 入口；3. 角色和交接；4. 需求到上线的流程和四个确认点；5. 日程和决策；6. 工具分工；7. 连接和授权；8. 规则；9. 模板索引；10. 常见问题和故障处理。
- 验收标准：10 章齐全；四个确认点都写清要交什么材料、怎么确认、不通过时怎么退回；每章的步骤都能照着做，没有空着的占位内容。

### T3 写 8 个模板（P0）
- 目标：在 templates/ 下写好 8 个模板，每个都附填写说明和一个简短示例。
- 各模板字段：
  - 需求说明：背景、目标、用户和场景、约束、验收标准、未解决的问题
  - 方案：功能清单、流程、页面和交互、数据和接口、任务拆分、风险和取舍
  - 任务：目标、输入、产出、验收标准、优先级、负责角色
  - MVP 演示：演示范围、步骤、录屏或链接、17 的反馈
  - 验收清单：逐条对照、证据、是否通过、遗留问题
  - 项目档案：项目简介、仓库、当前阶段、确认点记录、关键决策
  - 待拍板事项：问题、可选方案、建议、截止时间、结论
  - 交接消息：由谁交给谁、所处阶段、附件、要对方做什么
- 验收标准：8 个文件齐全；字段和上面的清单一致；方案模板里的任务包含目标、输入、验收标准和优先级。

### T4 写 docs/connectors.md（P0）
- 目标：写清下列工具怎么连接、怎么授权、失效后怎么重连：Notion、滴答清单（官方 Open API，OAuth）、GitHub、云端开发 agent、Codex、ClawBot 微信桥。其中滴答清单和微信桥已经接通。
- 验收标准：每个工具都写清前提条件、操作步骤、权限范围、怎么确认已经连上、失效后怎么重连；提到密钥的地方一律写成「通过加密输入框提供，存为环境变量」；在仓库里搜不到任何真实令牌；DeepSeek Harness 只写一句「已弃用」，不写接入步骤。

### T5 写 docs/schedule.md（P1）
- 目标：定义 Notion「项目事项」的字段（项目、事项、类型、状态、待我决定、截止时间、来源）和看板、日历、待我决定三个视图，并写清它和滴答清单「17项目日程」怎么同步。
- 验收标准：字段表完整；写明 Notion 是主数据，滴答清单只管提醒，只从 Notion 单向接收；写清如何去重、冲突时怎么处理。

### T6 写 docs/roles.md、pipeline.md 和 rules.md（P1）
- 目标：roles.md 写五个角色的职责和交接方式；pipeline.md 写从需求到上线的流程和四个确认点；rules.md 写三条规则：密钥只通过加密输入框提供、对外发消息要 17 同意、交付按高标准验收。
- 验收标准：内容和 SKILL.md 不矛盾；pipeline.md 里有一张 mermaid 流程图。

### T7 写 examples/xiju-liaoyu（P1）
- 目标：用戏剧疗愈项目（https://github.com/lature93-lang/xiju-liaoyu）从需求、方案到验收完整走一遍，做成样例。
- 验收标准：已脱敏，没有个人信息，也没有密钥。

### T8 存成 Grok Bot skill（P0）
- 目标：把 SKILL.md 和它引用的模板存成 Grok Bot 的 skill，名字叫 opc-ai-workbench。
- 验收标准：内容和仓库里的版本一致；skill 里写明仓库是唯一来源，要改先改仓库，再同步到 skill。

### T9 自查并提 PR（P0）
- 目标：开分支提 PR，并附上自查清单。
- 验收标准：PR 描述里写明自查结果，包括密钥扫描、链接检查和章节是否齐全；质检员按 acceptance 模板验收通过后再合并。

### 执行顺序
先做 T1；然后 T2、T3、T4 同时进行；接着做 T5 和 T6；再做 T7；最后依次完成 T8 和 T9。

## 四、风险和取舍
1. DeepSeek Harness：17 已确认弃用，文档里只保留一句说明。
2. 滴答清单 OAuth：已接通。令牌过期后需要 17 本人重新授权，文档里要写清重连步骤。
3. 微信 ClawBot 桥：已接通，但它是第三方桥接，稳定性和隐私不完全可控。微信掉线时，改用 Grok Bot 主窗口。
4. 仓库和 Grok Bot skill 各存一份，容易不一致：以仓库为唯一来源，改动先改仓库。
5. Codex 在本地执行时需要电脑在线，并且每条命令都要批准：速度慢但安全。云端能做的事不放到本地做。
6. Notion 和滴答清单两边都写可能产生重复：Notion 是主数据，滴答清单只单向接收提醒。
7. 密钥泄露：用 .gitignore 把密钥文件排除在外，提 PR 前做密钥扫描，两项都是验收的硬性条件。
